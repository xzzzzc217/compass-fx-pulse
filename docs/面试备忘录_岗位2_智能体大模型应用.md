## 3. JD 加分项① — RAG / 多 Agent / MCP / Skill

### 3.1 RAG 子系统（必懂概念 + 实现）

#### 你必须能讲清楚的 5 个 RAG 概念

**a) Embedding（嵌入）**
- 把文本转成定长向量（我们用的 bge-m3 是 **1024 维**）
- 同主题的句子向量夹角小（cosine 相似度高）
- 我们的 embedder 实现：把 bge-m3 当作 XLMRoberta，CLS pooling + L2 normalize（见 `app/rag/embedder.py`）
- 为什么不用 sentence_transformers / FlagEmbedding：Windows + transformers 5.x 下 sentence_transformers 加载 bge-m3 会 segfault；FlagEmbedding 1.4 调用了 transformers 5.x 移除的 API。所以我们走原生 transformers 实现稳定性更好

**b) 向量库（Vector DB）**
- 我们用 **ChromaDB**（本地 SQLite + DuckDB 持久化），不是 Qdrant / Milvus
- 为什么 Chroma：零基础设施（不用起 Docker），单 `pip install chromadb` + PersistentClient 落本地磁盘。如果数据量上到百万级再切 Qdrant
- 替代方案对比：
  - Chroma：小规模、本地、零配置 ✓
  - Qdrant / Milvus：千万级生产、有运维团队
  - FAISS：纯算法库，不带元数据过滤
  - PGVector：已有 PG 数据库时复用

**c) Chunk 切块策略**
- 我们的策略：**header-bounded + 600-char 硬上限 + 80-char overlap**（见 `app/rag/ingest.py`）
- 为什么 header-bounded：markdown 的 `##` 标题天然是语义边界
- 为什么 600 字 + 80 重叠：bge-m3 max_len=512 token，600 中文字符约对应 400-500 token；80 字 overlap 防止切到关键句中间导致召回漏掉
- **30 篇文档 → 切成 251 chunks**（这个数字要记住）

**d) Hybrid 检索：dense + rerank**
- 第一阶段：bge-m3 dense embedding → ChromaDB 取 top-20（cosine 相似度）
- 第二阶段：bge-reranker-v2-m3 cross-encoder 重排 → 取 top-5
- 为什么要两段：
  - dense 召回快但不精（双塔，query 和 doc 分别编码，丢上下文）
  - reranker 慢但精（cross-encoder，query 和 doc 拼接进同一个 BERT 算 attention）
  - 工业界标配：dense 召回 N（50-100）→ reranker 精排 K（5-10）
- 我们设了 `min_score=0.0` 阈值过滤无关结果

**e) Metadata 过滤**
- 每个 chunk 带元数据：`category`（currency/concept/risk/policy）+ `currency`（USD/JPY/...）+ `source_file`
- 用户问"日本央行政策"→ Agent 调用 `search_forex_knowledge(query='YCC', currency='JPY', category='policy')`
- ChromaDB 的 where 子句过滤：`{"$and": [{"currency": "JPY"}, {"category": "policy"}]}`
- 这是 Context Engineering 的实战体现：**先用结构化属性缩范围，再做向量召回**，比单纯向量更精

#### RAG 高频追问 Q&A

**Q：为什么用 bge-m3 不用 OpenAI text-embedding-3？**
A：三个理由：① 中文场景 bge-m3（BAAI 出品）效果优于 OpenAI；② 本地部署不外发数据，金融场景对隐私敏感；③ 自己控制版本、不被 API 限流。代价是要本地 GPU/CPU 跑一份 ~2.3GB 的模型。

**Q：rerank score 是什么意义？怎么定阈值？**
A：bge-reranker 输出的是单标签分类 logit。粗略说 >0 是相关，<0 是不相关，0 附近模糊。我们设 `MIN_RERANK_SCORE=0.0`，意思是只保留模型认为「相关」的片段。生产环境一般跑 100 题评测集找最佳阈值。

**Q：如果 RAG 召回的内容是错的怎么办？**
A：三层防御：① 切块时人工抽检 corpus 质量（30 篇都是 DeepSeek 合成 + 我抽检过）；② Agent 的 Reflector 会检查"概念问题是否引用了知识库"；③ 前端 Citation Card 把每条引用的 source + rerank_score 暴露给用户，让用户能验证。

**Q：怎么评价 RAG 系统效果？**
A：评测维度有 ① **Recall@K**（top-K 里包不包含答案所在 chunk）；② **MRR/NDCG**（相关 chunk 排在第几）；③ 端到端答案质量（用 LLM-as-Judge 或人工打分）。我们目前用 `tests/test_agent.py` 跑 10 个回归用例，把"应该走 RAG vs 应该走 SQL"两类问题的路由准确率盯住。

**Q：召回不到怎么办？**
A：返回 `{results: [], note: "no relevant passages found"}`，Agent 的 system prompt 让 LLM 在这种情况下"基于自己的训练知识回答，但要标注'知识库未覆盖此主题'"——避免 LLM 编造引用。

### 3.2 Function Calling Agent（核心理解必须扎实）

#### 你必须能讲清楚的 5 个 Agent 概念

**a) 什么叫 Function Calling**
LLM 厂商把"调用工具"做成了 native API。请求里带一个 `tools` 数组（每个工具有 name / description / JSON schema），LLM 收到用户问题后，要么直接回 content（普通回答），要么回 `tool_calls`（工具名 + 参数）。**LLM 不会真的执行工具，是它告诉你它想调什么**，由你的代码实际执行后把结果以 `role: "tool"` 塞回 messages 让它再消化。

**b) Agent 的循环结构（必须能默写）**
```
messages = [system_prompt, user_query]
while round < MAX_ROUNDS:
    resp = LLM(messages, tools=TOOLS)
    if resp.tool_calls:
        for tc in resp.tool_calls:
            result = execute(tc.name, tc.args)
            messages.append({role: "tool", name, content: json(result)})
        messages.append(assistant_with_tool_calls)
        continue
    else:
        return stream(resp.content)
```

**c) 我们的 5 个工具设计原则**
- 每个工具只做一件事（**单一职责**）
- description 写得"严谨且对照"——我特意在每个工具描述里写 `USE WHEN: ...` 和 `DO NOT USE for: ...`，模糊的描述会导致 LLM 滥调（见 `app/agent/tools.py:215-310`）
- 输入用 enum 限定（货币只能是 6 个之一），减少 LLM 编造无效参数
- 输出永远是 JSON serializable dict，错误也封装成 `{error: ..., hint: ...}`，不抛异常

**d) Prompt Engineering（系统提示词三层防御）**
我们的 system prompt 有三段：
1. **能力清单**：明确告诉 LLM 有哪些数据查询工具、哪些知识检索工具
2. **决策规则**：用具体例句区分"调数据工具 vs 调 RAG vs 不调任何工具"
3. **工具调用纪律**：禁止重复调用、禁止串行调用、拿到结果立刻综合

为什么这种细致写法重要：LLM 默认有"工具习惯性偏好"——给它工具它就想用；不写"DO NOT USE"，它会把"什么是 carry trade"也路由去 `get_exchange_rate`（USD 和 JPY 都满足 enum）。

**e) Context Engineering（上下文工程）**
JD 里专门列了这一项。具体含义：**控制塞进 LLM 上下文的内容质量和顺序**。我们做了：
- RAG 召回结果带 metadata（category / currency / score），LLM 能区分多个引用
- 工具结果用 `role: "tool"` 而非 `role: "user"`，符合 OpenAI 协议
- 工具失败时返回 `{error, hint}` 而非异常，让 LLM 能"读懂"错误
- 历史消息保留 assistant 的 tool_calls 字段（不能只保 content），否则 OpenAI API 会报错

#### Agent 高频追问 Q&A

**Q：MAX_TOOL_ROUNDS 设多少？为什么？**
A：我们设的是 **2**。绝大部分问题 1 轮工具够用；2 轮防止"先查汇率再做 VaR 计算"这种复合需求；4 轮以上几乎全是浪费——LLM 已经决定不了就让它把现有信息综合答出来更好。

**Q：怎么避免 LLM 乱调用工具？**
A：四个机制：① system prompt 显式区分调用场景；② 工具 description 写"USE WHEN / DO NOT USE for"对照范例；③ 跑 `tests/test_agent.py`，10 个 case 包含 1-2 个"应该不调用工具"的回归 case；④ Reflector 节点会检查"工具结果是否真的被用上"，如果回答没引用工具数据但调了工具，会被打低分。

**Q：tool_choice 你怎么设的？**
A：`tool_choice="auto"`，让 LLM 自己决定。其他选项是 `"none"`（强制不调）或 `{type:"function", function:{name:"xxx"}}`（强制调指定工具）。强制路由通常用在已知问题类型的场景，我们的对话式 Agent 不适合写死。

**Q：如果工具返回错误怎么办？**
A：错误透传给 LLM，但用结构化格式：`{error: "no data for USD/JPY on 2030-01-01", note: "..."}`。LLM 看到 error 字段就会如实告诉用户"系统中无此数据"，而不是编造数值。这比抛异常让 Agent 崩掉好得多。

**Q：流式输出（streaming）是怎么做的？**
A：我们在 Agent 循环外层用 SSE（Server-Sent Events）。前端 `/api/agent` endpoint 返回 `text/event-stream`，每条 event 是一行 `data: {json}\n\n`。Trace 事件（plan / tool_result / reflection）和文字事件（text）走同一条流。Streaming 实现见 `app/agent/core.py:_text_event` 和 `_trace_event`。

### 3.3 多 Agent 编排（LangGraph + Reflector）

#### 你必须能讲清楚的 4 个概念

**a) 什么叫"多 Agent / 状态机"**
不是"多个 LLM 在跑"，而是把单个 Agent 的任务拆成几个**逻辑节点**，每个节点用不同的 prompt 或不同的 LLM，节点间通过共享状态（State）传递数据。优点：① 每个节点职责单一，易调试；② 可以单独优化某个节点（比如 Reflector 用更便宜的小模型）；③ 可视化执行路径。

**b) LangGraph 是什么**
LangChain 团队出的 DAG 编排框架。核心概念：
- **State**：TypedDict，节点之间共享的数据（user_query / messages / draft / reflection）
- **Node**：一个 Python 函数，接收 state 返回 partial state（被自动 merge）
- **Edge**：直接边 `add_edge(A, B)` 或条件边 `add_conditional_edges(A, router_fn, mapping)`
- **START / END**：入口和出口节点

我们的实现见 `app/agent/graph.py`，5 节点：planner → executor → synthesizer → reflector → finalize。

**c) Reflector（反思纠错）设计**
- 输入：`(用户问题, 工具结果摘要, 助手草稿)`
- 输出严格 JSON：`{"score": 1-10, "issues": "...", "suggestion": "..."}`
- 评分维度（写在 system prompt 里）：
  ① 涉及数值时是否用了 tool 返回的真实数字（防幻觉）
  ② 概念问题是否引用了 RAG 段落
  ③ 是否编造 tool_results 中不存在的数据
  ④ 是否答非所问
- 阈值：**score ≥ 7 通过**；< 7 → 回 synthesizer 重写，把 issues + suggestion 作为额外 system prompt 注入；最多重试 1 次

**d) 双轨实现的工程意义**
我们 `core.py`（生产）和 `graph.py`（架构参考）两份代码。`core.py` 是线性 Python 流（首字延迟更可控、流式 UX 好），`graph.py` 用 LangGraph 显式状态机（架构清晰、可导出 mermaid 图）。**两份共享同一组 tools.py，不重复维护**。面试讲这点会被加分——展示工程审美。

#### LangGraph 高频追问 Q&A

**Q：你用 LangGraph 不用 LangChain Agent 是为什么？**
A：LangChain 的 AgentExecutor 是隐式循环，调试困难；LangGraph 是显式状态机，每个节点可单独 mock 测试，路由决策（route_after_planner 等）一目了然。生产 Agent 选择 LangGraph 是行业趋势——LangChain 自己在 2024 年就把"复杂 Agent"统一推到 LangGraph 上了。

**Q：Reflector 失败怎么办？会不会卡住用户？**
A：Reflector 调用失败 / JSON 解析失败 / 超时 → 默认返回 `score=10, _reflector_error=str(exc)`，**直接通过质量门**。理念是"observability 不应该破 user request"。错误信息只落到 Langfuse trace，前端看不到。

**Q：加 Reflector 后首字延迟变长，怎么解释这个 trade-off？**
A：是的，加了大约 3-5 秒。我们的取舍是"**质量门优先于流畅性**"——以前用户可能流畅地看到一段错答案；现在等一会儿但看到的是审过的答案。视觉上仍保留流式打字效果，办法是先收满草稿，再用 `_chunk_text(draft, 4)` 按 4 字一节往前端推。

**Q：Reflector 自己也是 LLM，会不会自己也错？**
A：会。所以我们：① temperature=0.0 让评审尽量确定；② max_tokens=300 限制别水；③ response_format=json_object 强制 JSON 输出；④ MAX_REFLECTION_RETRIES=1 避免无限重试。Phase 4 计划升级成"多专家投票"（Critic Ensemble）来降低单一 Critic 的偏差。

### 3.4 MCP（Model Context Protocol）

#### 你必须能讲清楚的核心概念

**a) MCP 是什么**
2024 年 11 月 Anthropic 公开的开放协议（[modelcontextprotocol.io](https://modelcontextprotocol.io/)），让 LLM 应用（**MCP Client**：Claude Desktop / Cursor / 我自己写的客户端）能发现并调用外部能力（**MCP Server**：把工具/资源/prompt 封装好的服务）。

**类比理解**：MCP 之于 LLM 工具集成，约等于 LSP 之于 IDE 语言服务——**统一协议，避免每对 client × server 都做适配**。

**b) MCP 协议层结构**
- 三类能力：
  - **Tools**：可调用函数（最常用）
  - **Resources**：只读资源（文件、数据库行）
  - **Prompts**：可复用的 prompt 模板
- 两种传输：
  - **stdio**：子进程方式启动 server，client 通过 stdin/stdout 收发 JSON-RPC（本地用，Claude Desktop 默认）
  - **HTTP/SSE**：远程调用，跨机器集成

**c) 我们的实现（FastMCP）**
- `backend/mcp_server/server.py`：用 `FastMCP("compass-fx")` 装饰器把 5 个工具暴露成 MCP tools，再加 1 个 resource（`compass-fx://corpus/{filename}` 读 corpus markdown）
- **关键设计**：MCP server 不重写工具，直接 `from app.agent.tools import execute`，加一层 FastMCP 装饰器适配协议格式。改一处工具，HTTP API + MCP 双入口同步生效——分层架构的体现

#### MCP 高频追问 Q&A

**Q：MCP 和 OpenAI Function Calling 有什么区别？**
A：层次不同：
- Function Calling 是**模型层 API**（OpenAI/DeepSeek/Anthropic 各家自己的 chat API 字段）
- MCP 是**应用层协议**（连接 LLM Client 和外部能力 Server 的标准）

我们这两套同时存在：Web Agent 走 Function Calling（DeepSeek API 的 tools 字段），Cursor / Claude Desktop 走 MCP（FastMCP server）。**两边共享同一份 `tools.py` 实现**——这是分层架构的体现。

**Q：MCP 的 stdio 模式怎么 debug？**
A：stdio 是 stdin/stdout 收发 JSON-RPC。Debug 的几个套路：
1. 写 stdio smoke test（见 `tests/test_mcp_server.py`），用 Python `subprocess` 起 server，写 init / list_tools / call_tool 三段消息
2. 把日志写到 stderr（Claude Desktop 会捕获），stdout 留给协议
3. Claude Desktop 的"Developer → MCP logs"能看协议级 traces

**Q：MCP server 启动慢怎么办？**
A：MCP server 是 stdio 子进程，每次 Claude Desktop 启动都新起一个 Python，bge-m3 + reranker 冷加载 30-60 秒。我们的应对：
- 默认 **lazy loading**——RAG 模型只在第一次调用时加载，避免"每次开 Claude Desktop 都等 60 秒"
- 加 `--warmup-rag` 选项，让重度用户可选启动时预热
- 如果是 HTTP 模式，可以用 nginx + 长连接保持

**Q：MCP 的安全模型？**
A：Claude Desktop 在第一次调用 MCP tool 时会弹**用户确认对话框**（Tool calls require approval），用户必须明确允许才会执行。这避免恶意 prompt 让 Claude 调用文件删除等危险操作。我们的工具都是只读 SQL + RAG 检索，没有写操作，所以风险很低。

## 4. JD 加分项③ — AI Infra（vLLM / Ollama / KV cache / 流式输出）

### 4.1 你需要诚实的事实

**项目实际没用 vLLM**——我们用的是 FastAPI + transformers 自己写 OpenAI 兼容服务（`llm/serve.py`）。**这是面试时一定要说清楚的事**，否则被追问"你 vLLM 哪里用的"会很尴尬。

但这不代表你不能在面试里答 AI Infra 问题，因为：
1. 我们的 serve.py 在协议层是 OpenAI 兼容的，**和 vLLM 的 wire format 完全一样**——切 vLLM 是改 .env 一行的事
2. 我们了解 vLLM / Ollama 的内部原理，能答原理题
3. 我们规划了 Phase 4 接 vLLM 提升吞吐——这是 roadmap 不是空话

### 4.2 你必须能讲清楚的 5 个 AI Infra 概念

**a) KV Cache（键值缓存）**
LLM 自回归生成时，每生成 1 个 token 就要把已有 token 重新跑一遍 attention。**naive 实现复杂度 O(n²)**。
KV Cache 的优化：把每层 attention 的 K（keys）和 V（values）矩阵缓存下来，每次新 token 只算新 query 对历史 K/V 的 attention。**复杂度降到 O(n)**。
代价：**显存爆炸**——每个 token 在每层都要存一份 K/V 张量。Llama-7B 在 4096 上下文下 KV cache 约占 2GB 显存。

**b) PagedAttention（vLLM 的核心创新）**
传统框架按 max_seq_len 一次性给每个 request 分配连续显存（**预先分配的 padding**），实际生成的 token 数往往远小于 max_seq_len，导致大量浪费（碎片化 + 内部碎片）。
vLLM 借鉴**操作系统虚拟内存分页**思路：把 KV cache 切成固定大小的 block（默认 16 token），用类似 page table 的映射来动态分配。**实测 KV cache 显存利用率从 ~40% 提升到 >95%**。

**c) Continuous Batching（动态批处理）**
传统 static batching：一批请求里最长的那个跑完了，整批才能下一步。vLLM 的 continuous batching：每个 step 都重新组 batch，谁先生成完直接退出，新请求立刻补位。**吞吐量比 HuggingFace transformers 高 10-24×**。

**d) Streaming Output（流式输出）实现原理**
- transformers 的 `TextIteratorStreamer`（我们 serve.py 用的就是它）：在另一个线程跑 `model.generate`，主线程从 streamer queue 拉 token，逐字 yield 出去。
- vLLM：异步迭代器原生支持 streaming，配合 PagedAttention 不用拷贝 KV cache。
- 协议层：用 SSE（Server-Sent Events）或 WebSocket 把每个 token 推到客户端。我们 `serve.py` 的 `/v1/chat/completions` 在 `stream=true` 时返回 `data: {"choices":[{"delta":{"content":"..."}}]}\n\n` 格式，OpenAI 兼容。

**e) Ollama 是什么 / 怎么用**
Ollama 是用户态 LLM 推理服务器，特色：
- 自动量化（GGUF 格式 Q4_K_M / Q5_K_M）
- 一键 pull 模型：`ollama pull qwen2.5:7b`
- 内置 OpenAI 兼容 API（`http://127.0.0.1:11434/v1`）

**我们项目的 .env 已经支持切到 Ollama**——只要把 `LLM_BASE_URL=http://127.0.0.1:11434/v1`，`LLM_MODEL=qwen2.5:7b-instruct` 就能用。这点在 README 表格里写明了。

### 4.3 AI Infra 高频追问 Q&A

**Q：你用 vLLM 吗？**
A：直接答："**没有**。我的本地 dev 环境是 Windows，vLLM 官方 Linux only，要部署得通过 WSL2，对单机 demo 不划算。我用 FastAPI + transformers 写了 OpenAI 兼容的 serve.py，**协议层和 vLLM 完全一致**，未来云上部署切 vLLM 是改 .env 一行的事。我了解 vLLM 的核心原理（PagedAttention、continuous batching、流式异步调度），但项目本身没跑 vLLM。"

**Q：那你怎么证明你了解 vLLM？**
A：见上面 "PagedAttention" + "Continuous Batching" 解释。然后补一句："vLLM 我看过 SOSP 2023 的 PagedAttention 论文（《Efficient Memory Management for Large Language Model Serving with PagedAttention》），知道它把 LLM serving 当作内存管理问题来解，是把 OS 经验迁移到 LLM 服务的经典案例。"

**Q：你的 serve.py 怎么实现流式输出？**
A：用 `TextIteratorStreamer` + 后台线程跑 generate + 主线程 yield。代码大概是：
```python
streamer = TextIteratorStreamer(tokenizer, skip_prompt=True)
Thread(target=model.generate, kwargs={..., "streamer": streamer}).start()
async def gen():
    for chunk in streamer:
        yield f"data: {json.dumps({...delta: chunk...})}\n\n"
return StreamingResponse(gen(), media_type="text/event-stream")
```
要点：① 必须开后台线程否则 generate 会阻塞；② 协议格式严格按 OpenAI SSE。

**Q：4-bit 量化是什么？什么时候用？**
A：把 fp16 weight（每个参数 2 字节）压成 4-bit 量化（每个参数 0.5 字节 + 一些 scale）。常见格式：
- **NF4**（QLoRA 论文用的）：信息论最优 4-bit 编码
- **GGUF Q4_K_M**：llama.cpp 的混合量化
量化用在两个场景：① 训练时显存不够（QLoRA）；② 推理时 CPU 跑大模型（llama.cpp）。
**坑**：我们 Phase 2 训练时实测 4-bit 反而比 BF16 慢（dequantize-on-forward 开销），8GB 显存放得下 BF16 时**不要量化**。

**Q：什么是 KV cache 优化？**
A：见 KV Cache 解释。补充一些工程优化：① **Sliding window attention**（限制只看最近 N 个 token，KV cache 大小 O(N) 而非 O(seq_len)）；② **Multi-Query Attention / Grouped-Query Attention**（多 head 共享 K/V，KV cache 显存砍 8-32×）；③ **量化 KV cache**（fp8 / int8）。

**Q：流式输出的延迟优化怎么做？**
A：分两个延迟：
- **TTFT（Time To First Token）**：用户等多久看到第一个字。受 prefill 速度（tokenize + 第一遍 forward）影响。优化：① warmup 加载模型；② vLLM PagedAttention 减少分配开销；③ Speculative Decoding（小模型先草稿，大模型并行验证）
- **TPOT（Time Per Output Token）**：每后续 token 多少毫秒。受 decode 速度影响。优化：① continuous batching；② INT8/FP8 量化；③ 模型蒸馏成小模型

我们 `serve.py` 量化的 `_load(quant="bf16")` 默认就是为最低 TPOT 调的——8GB 显存下 BF16 比 4-bit 快约 2×。

## 5. JD 加分项④ — SFT / RL 经验

### 5.1 LoRA SFT 你必须能讲清楚的概念

**a) LoRA 原理（30 秒版）**
全量微调 W 矩阵参数太多（Qwen3-1.7B 有 17 亿参数）。LoRA 假设"任务相关的 weight update ΔW 是低秩的"，把 ΔW 分解成两个矩阵的乘积 `ΔW = B × A`，A 形状 `(d, r)`、B 形状 `(r, d)`，**r << d**（我们用 r=16）。
训练时只更新 A、B；推理时把 `W' = W + BA` 合并回去（merge），无额外推理开销。

**参数量**：Qwen3-1.7B hidden=2048，每层每个 target 加 r=16 LoRA → 每个 target 约 65K 可训练参数 → 7 个 target × 28 layer ≈ 12M 可训练参数 → 占总参数 0.7%。

**b) 为什么选 LoRA 不全量微调**
- 显存：全量微调 1.7B 模型 + AdamW 优化器至少要 ~40GB 显存；LoRA 只训 12M 参数，8GB 笔记本能跑
- 数据：3K 数据下全参微调容易"灾难性遗忘"通用能力；LoRA 改动小，保留 base model 大部分能力

**c) 训练超参（每个数字面试都会被问）**
```
LoRA: r=16, alpha=32 (alpha/r=2 是经验值), dropout=0.05
Target modules: q_proj, k_proj, v_proj, o_proj + gate_proj, up_proj, down_proj
                (全 attn + MLP linear)
Batch:  per_device=2, grad_accum=8 → effective=16
Seq len: 512 (覆盖 95% 金融 Q&A，attention 计算砍 4×)
Epochs: 2 (3 epoch 在 200 zh 子集上易过拟合)
LR: 2e-4, cosine, warmup 5%
Optimizer: paged_adamw_8bit (bitsandbytes 提供，省显存)
Precision: BF16
Grad ckpt: 关闭（开启拖速 2×；8GB 不开也能跑）
```

**d) 数据工程**
- 总样本 **3194 条**（3035 训练 / 159 评测）
- finance-alpaca 3000 条（HuggingFace 通用金融）+ 自合成 194 条中文外汇 Q&A
- **混训理由**：纯 finance-alpaca 中文外汇政策答得不专；纯自合成数据量太少（200）会过拟合
- **自合成方法**：50 个外汇主题 seed × 6 个角色变种（CFO / 散户 / 交易员 / 记者 / 机制 / 案例）→ DeepSeek 用 JSON-mode 生成 `{question, answer}`，温度 0.7，单条成本 ~¥0.0025

**e) 训练成果数字**
- eval loss: 4.85 → 1.30
- 单卡 RTX 4060 8GB 训完：约 65 分钟（早停 epoch 1）
- 训前 vs 训后金融 QA 对比见 `llm/output/comparison.md`

### 5.2 SFT 高频追问 Q&A

**Q：r 为什么选 16 不是 8 或 32？**
A：经验值。r=8 在中文 SFT 上欠拟合（领域特征学不到）；r=32 训练慢但效果增益不显著（PEFT 论文 Fig.5 拐点在 r=16-32）。同时 alpha=32（alpha/r=2）是 QLoRA 论文推荐配比。

**Q：为什么 target modules 要 attn + MLP 全选，不只选 attn？**
A：attn 影响"看哪里"（指代理解），MLP 影响"想什么"（领域知识表达）。金融领域 voice 需要 MLP 也微调，所以全选。如果只是格式跟随（比如学 JSON 输出）选 q/v 就够。

**Q：4-bit 量化 vs BF16 怎么选？**
A：我们实测在 RTX 4060 8GB 上：BF16 每步 10s（关 grad_ckpt），4-bit NF4 每步 28s（dequantize 开销）。**显存够时不要量化**。量化只在 ≥7B 模型 + 笔记本 GPU 这种"显存装不下 BF16"的场景才有意义。

**Q：怎么知道有没有过拟合？**
A：eval set 看 loss——eval_loss 持续下降说明还在学；train_loss 下降但 eval_loss 反弹就过拟合。我设 eval_steps=100，全程 4 个 eval point，足够看趋势。如果 eval_loss 在 epoch 2 反弹明显就早停。

**Q：DeepSeek 已经够强了为什么自训 1.7B？**
A：三个理由：① **隐私**——金融数据不出本地，蚂蚁很关心；② **延迟/成本**——本地推理 30+ tok/s 零成本 vs DeepSeek 每次 ¥0.001；③ **领域 voice**——自训模型回答更"项目化"，能用项目术语和语气。

**Q：自合成数据怎么保证质量？**
A：用更强模型（DeepSeek）当标注模型——这是 distillation 思路。强制 JSON output；prompt 里禁止编造具体数值；只占总数据 6% 不主导模型行为；Phase 4 计划引入人工 spot-check + LLM-as-Judge 做评估。

**Q：你做 RL 吗（PPO / GRPO / DPO）？**
A：直接答："**没做**。我做的是 SFT。RL 阶段需要 reward model 或人工 preference 数据，对个人项目的数据规模不现实。但我了解 PPO（OpenAI 用的，有 actor/critic 双 loss）、GRPO（DeepSeek-R1 用的，去掉 critic 用组内相对奖励）、DPO（直接从 preference pair 学，无需 RM）。Phase 4 计划用 100 题人工标 preference pair 做 DPO 实验。"

**Q：模型幻觉怎么处理？**
A：三层防御：

3. **Reflector 评分**：抓"编造工具未返回的数据"的 bad case（这是 Reflector 的 4 类典型 bad case 之一）

### 7.3 选型决策类（每个都要能给 3 备选 + 选择理由）

**Q：为什么 ChromaDB 不 Qdrant / Milvus / FAISS / PGVector？**
A：见 RAG 章节 b）。

**Q：为什么 bge-m3 不 BCE / m3e / text-embedding-3?**
A：bge-m3 中英双语 + 1024 维 + 支持 dense/sparse/colbert 三类（虽然我们只用 dense）。BCE 是网易的，效果略弱。m3e 老一些。OpenAI text-embedding-3 闭源 + 不能本地。

**Q：为什么 LangGraph 不 AutoGPT / CrewAI / MetaGPT？**
A：AutoGPT 是 2023 早期通用 Agent，不可控；CrewAI 重 multi-agent collaboration，对单 Agent + 工具循环过设计；MetaGPT 偏软件开发模拟。LangGraph 简洁、显式、和 LangChain 生态打通。

**Q：为什么 FastMCP 不裸写 MCP？**
A：FastMCP 是 MCP Python SDK 的高层封装，装饰器写法（`@mcp.tool()`）从函数签名 + docstring 自动生成 schema。裸写要手撸 JSON-RPC 协议层，对项目意义不大。

## 9. 你不要犯的 5 个错误

1. **不要说"vLLM 我用过"**——明明没用，被追问就崩。说"了解原理 + roadmap 要切"
2. **不要说"PPO/RL 我做过"**——明明只做了 SFT，被追问"你的 reward model 怎么设计"会跪
3. **不要说"我自己写的全部代码"**——AI 协助是事实，承认且强调架构决策是你做的
4. **不要把数字记错**——LoRA r=16, alpha=32, bs=2/ga=8, eval loss 4.85→1.30, RAG 30 篇 251 chunks, MAX_TOOL_ROUNDS=2, Reflector 阈值=7。这些数字面试当场会被问
5. **不要回避不会的问题**——直接说"这块我没深入做过，但我知道 X 是怎么回事，会快速补上"
